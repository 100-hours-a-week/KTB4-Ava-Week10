# 회고

## 들어가며

프론트엔드 개발을 시작한 지는 꽤 됐지만 Vanilla JavaScript를 기반으로 프로젝트 전체를 진행해본 경험은 없었습니다.

이번 프로젝트를 진행하면서 과거를 돌아보니 조금 부끄럽지만 **JavaScript 자체를 충분히 이해하지 못한 상태에서 프론트엔드 프레임워크를 사용해왔던 것이 아닌가** 하는 생각이 들었습니다.

React를 사용할 때는 컴포넌트와 state를 사용하는 것이 자연스럽게 느껴졌지만, Vanilla JavaScript로 직접 화면을 만들어본 뒤에는 React가 어떤 불편을 대신 해결해주고 있었는지를 이전보다 명확하게 이해하게 됐습니다.


## Vanilla JavaScript를 경험하고 React를 다시 이해하게 됐다

Vanilla JavaScript에서는 화면 상태가 변경될 때 DOM을 직접 찾아서 수정해야 했습니다.

```text
데이터 변경
→ 변경할 DOM 탐색
→ text/class/attribute 직접 변경
→ 관련 이벤트와 화면 상태 동기화
```

기능이 적을 때는 큰 문제가 없었지만 화면이 복잡해질수록 JavaScript에서 가지고 있는 상태와 실제 DOM 상태를 계속 맞춰야 하는 것이 불편했습니다.

DOM을 직접 조작하면서 사용자 입력을 어떤 방식으로 화면에 삽입하는지도 더 신경 쓰게 됐습니다.

React를 사용할 때는 이전부터 당연하게 사용했던

```text
상태
↓
UI 선언
↓
상태 변경
↓
화면 갱신
```

이라는 구조가 왜 필요한지를 Vanilla JavaScript를 경험한 뒤에야 더 명확하게 이해했습니다.

React가 무조건 Vanilla JavaScript보다 좋은 기술이라는 의미는 아닙니다.

이번 경험을 통해 **기술을 선택할 때 "많이 사용하니까"가 아니라 지금 겪고 있는 어떤 문제를 해결하기 위해 선택하는지를 설명할 수 있어야 한다**고 느꼈습니다.


## Vanilla JavaScript에서 React로 마이그레이션하며 설계부터 시작했다

프로젝트 중간에는 기존 Vanilla JavaScript 기반 프론트엔드를 React로 마이그레이션했습니다.

처음에는 기존 HTML과 JavaScript를 React 컴포넌트로 옮기면 될 것이라고 생각했습니다. 하지만 바로 코드를 수정하기보다 먼저 **현재 프로젝트가 어떤 구조로 동작하고 있는지 파악하는 작업이 필요하다**고 판단했습니다.

그래서 마이그레이션 전에 별도의 설계 문서를 작성했습니다.

```text
기존 프로젝트 구조 파악
→ 반복적으로 사용하는 UI 요소 확인
→ 컴포넌트화할 영역 결정
→ 페이지별 상태와 이벤트 흐름 확인
→ API 호출 위치와 공통 로직 확인
→ 기존 라우팅 방식 확인
→ React에서의 대응 방식 결정
→ 페이지 단위로 순차 마이그레이션
```

특히 기존 코드에서 반복적으로 사용되는 UI라고 해서 모두 컴포넌트로 분리하지 않고, 실제로 상태와 동작을 함께 공유하는지 확인한 뒤 컴포넌트 경계를 정하려고 했습니다.

라우팅 역시 기존의 `<a>`, `window.history`, `popstate` 기반 흐름을 그대로 흉내 내기보다 React Router와 navigation hook을 사용하는 React 방식으로 전환했습니다.

이 과정을 통해 마이그레이션은 단순한 문법 변환이 아니라 **기존 동작을 먼저 이해하고, 무엇을 유지하면서 어떤 책임을 새로운 구조로 옮길지 결정하는 작업**이라는 것을 경험했습니다.

### AI가 프로젝트 맥락을 잃지 않도록 컨텍스트도 문서화했다

프론트엔드 구현에는 AI를 많이 활용했기 때문에, 마이그레이션 과정에서 또 다른 문제가 있었습니다.

작업을 여러 번 나누어 요청하다 보면 AI가 이전에 결정했던 구조나 현재 마이그레이션 단계, 변경하면 안 되는 범위를 놓치면서 필요하지 않은 리팩터링을 하거나 이미 정한 방향을 다시 바꾸는 경우가 있었습니다.

그래서 단순히 매번 긴 프롬프트를 다시 작성하기보다 **프로젝트의 전제와 작업 기준을 별도의 컨텍스트 문서로 정리해 사용했습니다.**

문서에는 다음과 같은 내용을 남겼습니다.

```text
현재 프로젝트 구조
현재 마이그레이션 단계
기존 동작 중 반드시 유지할 부분
React에서 사용할 방식
컴포넌트 분리 기준
API 호출 구조
수정해야 할 파일
수정하지 말아야 할 범위
검증해야 할 동작
```

그리고 실제 작업을 요청할 때도 가능한 한

```text
어디를 수정하는지
무엇을 수정하는지
왜 수정하는지
유지해야 하는 동작은 무엇인지
하지 말아야 할 변경은 무엇인지
어떻게 검증할 것인지
```

를 명확하게 전달했습니다.

작업 범위나 기존 구조를 제가 정확히 파악하지 못한 경우에는 바로 구현을 요청하기보다 먼저 Plan mode로 관련 코드와 영향 범위를 확인하게 했습니다. 불필요하게 전체 코드를 다시 읽거나 잘못된 방향으로 구현한 뒤 되돌리는 작업을 줄이고 싶었기 때문입니다.

처음에는 AI 활용 능력을 좋은 프롬프트를 작성하는 능력이라고 생각했습니다.

이번 마이그레이션에서는 생각이 조금 바뀌었습니다.

**AI에게 많은 코드를 작성하게 하는 것보다, 현재 시스템의 맥락과 변경 범위를 문서화하고 작업을 작은 단위로 제한한 뒤 결과를 검증하는 것이 더 중요했습니다.**

마이그레이션 설계 문서와 AI 컨텍스트 문서를 실제 작업에 사용하면서, AI를 단순한 코드 생성 도구보다 기존 프로젝트의 제약 안에서 작업하도록 관리하는 도구로 사용하는 경험을 할 수 있었습니다.


## React의 어려움은 화면보다 비동기 상태에 있었다

React 전환 이후 가장 까다로웠던 부분은 컴포넌트를 만드는 것보다 여러 비동기 요청을 함께 관리하는 것이었습니다.

대표적인 문제가 access token 만료였습니다.

게시글 상세 화면에서는 게시글, 댓글, 사용자 정보 등의 요청이 비슷한 시점에 발생합니다.

access token이 만료돼 모든 요청이 동시에 401을 받으면 각각 refresh 요청을 실행할 수 있었습니다.

그래서 공통 API client에 `refreshPromise`를 두었습니다.

```text
여러 요청 → 동시에 401
          ↓
첫 요청만 refresh 시작
          ↓
나머지 요청은 같은 Promise 대기
          ↓
access token 갱신
          ↓
기존 요청 각각 한 번만 재시도
```

인증 복구 정책 역시 개별 페이지에서 처리하지 않고 공통 API client로 모았습니다.

여기서 **프론트엔드의 상태가 컴포넌트의 `useState`에만 존재하는 것이 아니라는 점**을 느꼈습니다.

현재 진행 중인 refresh 요청과 같이 여러 요청이 함께 알아야 하는 상태 역시 애플리케이션의 중요한 공유 상태였습니다.

## 자동저장은 debounce만으로 해결되지 않았다

게시글 작성 화면에는 임시저장 기능이 있었습니다.

처음에는 사용자가 입력을 멈춘 뒤 일정 시간이 지나면 저장하는 debounce 정도로 생각했습니다.

하지만 실제로는 다음 상황들이 겹쳤습니다.

```text
autosave 진행 중
+
사용자가 새 입력
+
최종 등록 버튼 클릭
```

진행 중인 저장이 이전 입력을 기준으로 하고 있는데 그 사이 새로운 입력이 발생하면, 어떤 상태가 서버의 최신 상태인지 구분해야 했습니다.

임시저장 ID가 아직 확정되지 않은 상태에서 최종 등록이 실행될 가능성도 있었습니다.

그래서 다음 정보를 명시적으로 관리했습니다.

```text
temporaryIdRef
→ 확정된 임시저장 ID

inFlightSaveRef
→ 현재 진행 중인 autosave

editVersionRef
→ 저장 시작 이후 입력이 변경됐는지 확인

saveQueuedRef
→ 저장 중 새 입력 발생 여부

lastSavedFileRef
→ 동일 파일 중복 업로드 방지
```

최종 등록 시에는 진행 중인 autosave가 있다면 먼저 완료될 때까지 기다린 뒤 확정된 임시저장 ID로 게시글을 생성하도록 했습니다.

이 경험을 통해 **비동기 기능에서는 요청을 보냈는지만 보는 것이 아니라, 그 요청이 어느 시점의 데이터를 가지고 있는지를 추적하는 것이 중요하다**는 것을 배웠습니다.


## 같은 UI라도 도메인의 의미가 다르면 동작도 달라야 했다

모임 게시글에서는 댓글이 단순 댓글이 아니라 참여 신청의 의미를 가졌습니다.

기존 댓글 UI를 그대로 사용하면 참여 댓글에도

```text
답글
수정
삭제
```

기능이 노출됐습니다.

하지만 모임의 정책에서는 한 번 작성한 참여 신청 댓글을 일반 댓글처럼 수정하거나 삭제할 수 없었습니다.

그래서 같은 `CommentTree`를 사용하더라도 모임 게시글인지에 따라 가능한 액션을 분리했습니다.

또 참여 신청이 성공한 뒤 댓글 목록만 다시 불러오면 모집 인원과 progress bar는 기존 값으로 남았습니다.

모집 인원과 모집 상태는 서버가 관리하는 값이므로 참여 성공 후 게시글 상세 정보도 다시 조회하도록 변경했습니다.

이 경험에서 **컴포넌트를 재사용하는 것 자체보다 해당 UI가 도메인에서 어떤 의미를 가지는지가 우선**이라는 것을 느꼈습니다.

모양이 같은 댓글이라도 일반 게시글과 모임 게시글에서 의미가 다르면 허용되는 행동도 달라져야 했습니다.


## 프론트엔드와 서버 사이에도 여러 계층의 계약이 있었다

이미지 업로드에서도 비슷한 문제가 있었습니다.

프론트에서는 이미지 확장자만 확인하고 있었지만 실제 요청은 Nginx를 통과하기 때문에 파일 크기 역시 proxy의 제한을 받습니다.

예를 들어 3MB 제한이 있다면,

```text
프론트
→ 3MB 이하인지 검사

Nginx
→ client_max_body_size 3m

API client
→ 413 응답을 동일한 사용자 메시지로 변환
```

처럼 각 계층의 기준을 맞춰야 했습니다.

프론트에서 허용한 파일을 Nginx가 거절하면 사용자는 제출한 이후에야 실패를 알게 됩니다.

또 Nginx에서 발생한 413은 백엔드에서 사용하는 공통 오류 응답 형식과 다를 수 있기 때문에 HTTP status를 이용한 별도 fallback도 필요했습니다.

백엔드에서 API 계약을 고민했던 것처럼, 프론트에서도 **브라우저 → reverse proxy → 서버 사이에서 같은 규칙이 유지되어야 한다**는 것을 경험했습니다.

## 프론트엔드 구현에는 AI를 적극적으로 활용했다

이번 개인 프로젝트에서는 이전에 경험하지 못했던 백엔드 개발에 더 집중하고 싶었습니다.

그래서 프론트엔드 기능 구현과 수정에는 AI를 비교적 많이 활용했습니다.

다만 단순히 기능만 요청하는 방식은 피하려고 했습니다.

가능하면 먼저 다음을 명확하게 전달했습니다.

```text
수정할 위치
수정해야 할 동작
현재 동작
반드시 유지할 부분
수정하면 안 되는 영역
검증 방법
```

구조가 명확하지 않은 상태에서는 바로 코드를 수정하게 하기보다 Plan mode를 사용해 먼저 코드의 위치와 변경 범위를 파악하도록 했습니다.

React 마이그레이션에서도 프로젝트의 기존 구조와 결정 사항을 반복해서 잃지 않도록 별도의 컨텍스트 문서를 작성해 사용했습니다.

이전에는 AI 활용 능력을 좋은 프롬프트를 작성하는 능력 정도로 생각했습니다.

이번에는 조금 다르게 느꼈습니다.

**작업 범위를 정의하고, 하지 말아야 할 변경을 제한하고, 결과를 검증할 수 있는 기준을 제공하는 것까지가 AI 활용의 일부**라고 생각하게 됐습니다.

## 프론트엔드에서 가장 아쉬웠던 점

가장 아쉬웠던 것은 테스트였습니다.

이전에도 프론트엔드 테스트를 제대로 작성해본 경험이 없어 이번 프로젝트에서는 적용해보고 싶었습니다.

하지만 처음 경험하는 백엔드 구현과 테스트에 예상보다 많은 시간이 필요했고 프론트엔드 테스트까지 진행하지 못했습니다.

지금 다시 본다면 특히 다음 흐름은 자동 테스트를 작성해보고 싶습니다.

```text
동시 401
→ refresh 한 번만 실행
→ 원 요청 복구

autosave 중 새 입력
→ 최신 값 저장

autosave 중 최종 등록
→ 임시저장 완료 후 등록

모임 참여
→ 댓글 + 모집 상태 함께 갱신
```

여러 비동기 상태가 함께 움직이는 기능일수록 수동으로 반복 검증하는 것보다 테스트의 가치가 크다고 느꼈습니다.

렌더링 성능 개선도 관심이 있었지만 진행하지 못했습니다.

## 프론트엔드에서 가장 크게 달라진 점

이번 프로젝트 전에는 React의 사용법을 알고 있다고 생각했습니다.

Vanilla JavaScript에서 직접 DOM을 다뤄보고, 다시 React로 마이그레이션하고, 인증 복구와 autosave처럼 복잡한 비동기 상태를 관리하면서 생각이 달라졌습니다.

이제 React를 단순히 컴포넌트를 쉽게 만드는 라이브러리라기보다 **상태를 중심으로 UI를 관리하기 위한 구조**로 조금 더 이해하게 됐습니다.

또 프론트엔드 역시 단순히 화면을 그리는 영역이 아니라

```text
사용자 입력
클라이언트 상태
진행 중인 비동기 작업
서버 상태
실제 화면
```

을 일관되게 유지해야 하는 영역이라는 것을 경험했습니다.

## 앞으로 더 해보고 싶은 것

개인 프로젝트 기간 이후에는 다음을 추가로 진행하고 싶습니다.

* React Testing Library 또는 Vitest 기반 테스트
* 인증 refresh와 autosave hook 테스트
* Playwright 기반 주요 사용자 흐름 E2E 테스트
* React Profiler 기반 실제 렌더링 횟수 측정
* 측정 결과를 기반으로 한 렌더링 성능 개선

이번에는 백엔드에 우선순위를 두면서 하지 못한 영역이지만, 이후에는 기능 구현에서 끝내지 않고 **프론트엔드도 테스트와 측정을 통해 안정성과 성능을 확인하는 경험**까지 이어가고 싶습니다.
